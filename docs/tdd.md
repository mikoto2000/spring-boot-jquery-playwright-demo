## 登録・更新・削除の失敗と DB ロールバック（2026-10-22）

- **Red / DB**: 実際の H2 SQL 実行直後に SQLException を投げるテストを追加。正常時のコミット3件は成功したが、障害時の3件は登録行が残る・更新値が残る・削除行が戻らないという理由で失敗。テストメソッド自身にはトランザクションを付けていない。
- **既存挙動の確認 / E2E**: 登録・更新・削除の HTTP 500 をそれぞれ再現。入力保持、操作の再有効化、キャンセル、一覧・集計と実 API の全レコード不変、再試行成功を先にテスト化。これら3件はアプリを変更せず成功した。
- **Red / E2E**: 実際の DELETE を成功させ、その後の GET だけを503にするケースを追加。DB では消えているのに一覧に行が残り、期待0行に対し1行で失敗。
- Red のテストと依存関係を `2c642f3` に保存。
- **Green / DB**: Repository の登録・更新・削除に `@Transactional` を追加。SQL が1行を変更したこと、失敗時に全レコードが操作前と一致すること、障害時の autoCommit=false、正常時に変更が保存されることを検証し、6件が成功。
- **Green / E2E**: DELETE の成功応答後、ローカルの一覧から対象を除いて集計を再描画。その後の GET が失敗しても成功済みの削除を保持し、再取得できるように修正。Chromium・WebKit の既存・追加テスト計24件が成功。
- 重複する3操作のシナリオはパラメーター化し、SQL 障害注入もテスト専用ラッパーで共通化。正常系と異常系を同じ実 DB・Repository で検証する。
- CI の `mvnw package` でも結合テストが実行され、`database-test-reports` アーティファクトに Surefire の XML・テキストを保存する。

## 登録・更新成功後の一覧取得失敗（2026-10-22）

- **Red**: POST / PUT を実サーバーで成功させた直後、ブラウザからの一覧 GET だけを503にする2ケースを追加。成功メッセージと一覧取得エラーは表示されるが、登録行・更新値が見つからず、両ケースが失敗。テストを `0ac6716` に保存。
- **Green**: 登録 API では DB の生成キーを取得し、登録・更新 API は成功メッセージと保存済みレコードを返す。画面は応答の ID で一覧を追加・置換し、ID 順に整列して集計を更新してから GET を行う。
- 一覧取得が繰り返し失敗しても保存済みの値と集計を保持し、GET の再試行と再読み込み後も同じ値・ID・件数であること、POST / PUT が1回だけであることを確認。
- 再取得成功時は GET の200応答と読み込み終了を待って検証する。空の alert は CSS で非表示になるため、「空の可視要素がある」ではなく「エラーが見えない」を検証するようテスト側も修正。
- ローカルの DB 結合テスト6件が成功。Chromium・WebKit で既存12ケース×2ブラウザが成功し、追加2ケース×2ブラウザも修正後に成功。
